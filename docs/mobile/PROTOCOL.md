# Cere mobile protocol 1.1

[`client.schema.json`](../../protocol/mobile/v1/client.schema.json) is generated from the strict gateway allowlist; [`CONTRACT.json`](../../protocol/mobile/v1/CONTRACT.json) describes wire DTOs and cryptographic transcripts. Regenerate with `node tools/mobile-contract.ts`, verify with `node tools/mobile-contract.ts --check`. Public, non-secret canonicalization/hash/DER-signature vectors are in [`signing-fixtures.json`](../../protocol/mobile/v1/signing-fixtures.json) and are consumed by Node and Kotlin tests. [`conformance.json`](../../protocol/mobile/v1/conformance.json) holds response and event frames recorded from a real gateway (`tests/mobile-conformance.test.ts`, regenerate with `CERE_UPDATE_CONFORMANCE=1`) plus hand-written forward-compatible frames; Android `ConformanceTest` decodes every one. `--check` also fails when `CONTRACT.json` omits an operation or negotiated feature.

## Transport and authority

Only `wss://<approved-IP>:8443/mobile/v1` with subprotocol `cere.mobile.v1` is accepted. No browser Origin, compression negotiation, discovery broadcast or network pairing endpoint is supported. Android uses a dedicated certificate/SPKI-pinned client with validity and SAN checks. Public key encodings and unpadded base64url are canonical. RFC 8785 JSON is hashed with SHA-256; P-256 ECDSA signatures use DER, not P1363.

Offline offers include the identity public key, certificate, endpoints, nonce, five-minute expiry and signature. The phone response proves possession of both connection and per-use action keys. Local six-word comparison and desktop confirmation are mandatory before a device can connect. Keys never leave Android Keystore.

`hello → auth.challenge → auth → welcome` authenticates a 15-minute connection. The authentication signature binds the exact hello digest, challenge, desktop/device/key identity and broker epoch. Welcome advertises supported, capability-filtered operations. `sendAuthentication: "connection-key"` additionally advertises that exact `sessions.send` proofs may use the background connection key. An older broker that omits the field retains the legacy action-key requirement; clients that require passwordless Send should explain that the desktop broker must be restarted or updated instead of silently prompting for every message. Unknown methods/fields are rejected. No provider credential, native thread ID, MCP token, arbitrary filesystem handle or full desktop snapshot is sent.

Android pings the socket every 30 seconds; a missing reply closes it and reconnects with jittered backoff (1 s doubling to 60 s, then every five minutes once the desktop has been unreachable for ten). Reconnection stops only when the pairing no longer matches the desktop (certificate, pin or desktop identity mismatch, an expired certificate, missing phone keys), on revocation, for an incompatible version or authentication mode, or for `UNAUTHENTICATED` refusals that persist for at least three minutes across four attempts; the phone then explains whether a replacement pairing is needed. The desktop enforces challenge expiry; the phone derives its clock offset from the challenge instead of comparing expiry with its own clock.

Signed mutations first request a 30-second `commands.challenge` for their exact method, parameter digest and command ID. Android signs the operation together with the current device grant, authenticated connection and epoch. When negotiated through welcome, `sessions.send` uses the connection key without a password, fingerprint or other per-message prompt; the exact text, attachments, search choice, revisions and command ID remain signed. The legacy action-key proof is still accepted for Send. Every other proof-required mutation uses the per-use authenticated action key. Deny, Cancel, Stop, Pause, draft synchronization and other narrowly enumerated reductions retain a connection-authenticated path without biometrics. The broker rechecks scope, revision and policy at execution boundaries.

## State, revisions and outcomes

Session summaries include `draftIncluded:false`; only a hydrated session supplies its authoritative draft. `sync.open.sessionIds` is authoritative for removal even when only the first 50 summaries fit in the response. `sessions.list` pages additional summaries. Settings/session/draft revisions use decimal strings. Memory revisions additionally reject values beyond JavaScript's exact integer range before conversion to the canonical worker.

This implementation always reconciles an authoritative scoped snapshot on reconnect. Its opaque cursor is an invalidation hint, not an incremental replay promise. `sync.ack` acknowledges client persistence but does not currently prune or resume a server replay window. Android batches encrypted cache writes (about one write per second, flushed when the app leaves the screen) and acknowledges a cursor only after the state containing it is written. The server journals references/invalidations for 24 hours/10,000 entries without old transcript bodies. A changed transcript `cacheEpoch` forces cached message replacement, including after local memory erasure. Live messages are whole accumulated upserts with monotonic revisions.

`sessions.read` clears a conversation's Unread mark for every client, as opening it on the desktop does; Android sends it when an unread conversation is opened. It is a connection-authenticated reduction like rename and Stop. The `notice` event carries completion, error and interruption notices for in-scope conversations (`{kind, sessionId, title}`) and, for a device with `desktop.control` and the timers category, notices for timers started in its granted projects (`{kind: "timer", projectId, timerId, label}`). Approval requests are not sent as notices; they arrive through snapshots.

Message previews are selected directly from SQLite with bounded substrings. Pages budget 384 KiB before their envelope. Truncated content declares its length/revision and is fetched through `sessions.messagePart` in Unicode-scalar parts. Android has an assembly ceiling and never silently presents a shortened message as complete. Conversation pages contain user/assistant text only; `activity.list` contains tool, reasoning, and status records, so activity cannot crowd replies out of a chat page. Activity stays literal and copyable, and Android merges live revisions into the separate panel.

Every mutation has a per-device durable command ID and exact-parameter digest. A matching retry returns the retained outcome without execution; changed input under the same ID is rejected. Accepted/running commands become unknown after a broker restart. External effects followed by lost acknowledgement remain unknown. Use `commands.status` with the original ID; do not manufacture a replacement action after a timeout. Send returns accepted only after provider acceptance, after draft/configuration checks. Pre-dispatch failures preserve the draft and create no user transcript row. A lost acknowledgement after dispatch is unknown; the original command ID remains deduplicated. Android serializes autosave before signing and keeps snapshot/draft revisions monotonic. An uncertain send blocks another send until reconciliation or explicit review on the PC; acknowledging that review never replays the operation. Android lists every unconfirmed action in Settings for the same review. Unknown draft saves, renames, pins, read markers, Stop requests and upload steps are dropped, because the next snapshot shows their effect; an unknown approval answer is dropped once a snapshot has been applied, so a request that still exists can be answered again. An answer still in flight blocks only the request it answers. Desktop scripts and memory operations currently retain the RPC until completion; disconnection still does not authorize a replay.

Command results are bound to the accepting device scopeVersion and redacted after grants change. Memory invalidation also removes retained result/error content. ID tombstones survive result retention, preserving duplicate suppression. Scope reduction purges phone caches and pending sensitive parameters; policy errors distinguish revoked devices, temporarily disabled remote access and changed grants.

Error messages are written for people. The broker passes through messages it authored for the phone (control characters removed, at most 400 characters) and maps other codes to fixed explanations that name the next step; Android shows the message without the code. `APPROVAL_GONE` means the approval ID no longer exists. A changed proposal or capture digest returns `REVISION_CONFLICT` and requires fresh review. Android removes approvals after a confirmed answer or an authoritative gone response and refreshes changed requests; a delayed snapshot cannot restore a request retired during that snapshot. Transport failures and unknown command outcomes never count as approval success or authorize a replay.

The desktop gateway has no per-second/per-minute request or reconnect budgets and no history/memory cooldowns. Simultaneous-operation and capacity checks remain separate (`SESSION_BUSY` / `LIMIT_EXCEEDED`); authentication, expiry, scope and exact-action signatures still apply to every request.

## Media and companion parity

Uploads use signed begin/commit and one acknowledged chunk at a time. A binary frame contains a 16-byte UUID, unsigned 8-byte big-endian offset and at most 256 KiB of data. Status returns the contiguous committed offset. Phone drafts persist upload IDs/offsets for explicit resume, never automatic Send. Aborting removes a partial object.

Images are PNG/JPEG/WebP, at most 10 MiB each, four/20 MiB per send, 40 megapixels and 16,384 pixels per dimension. Desktop verifies size, SHA-256, magic and complete single-frame decoding. Per-device staging is 100 MiB; total retained media is bounded by 256 records/512 MiB per device and 2 GiB globally. Partial uploads expire after 15 minutes; unattached ready images after one hour. Android stores each upload's `expiresAt`; when the desktop has discarded an image (`ATTACHMENT_INVALID`) the phone keeps its private copy, offers Upload again and can always remove it locally. Submitted native-provider path inputs remain until explicit cleanup/revocation/session removal. Completed Ollama inputs can be deleted after their bytes are retained in provider history.

Saved capture approval previews are device/proposal/digest-bound, expire in five minutes and contain a ≤1 MiB derivative. Allow requires a verified complete preview and exact original-image digest. Only Ollama can currently consume the pinned immutable original bytes; native-provider capture Allow is withheld, while Deny and Stop remain available. There is no arbitrary image/path read endpoint.

Handoff copies a bounded eight-message preview into a new, reviewed draft without sending. Native history yields short-lived, single-use import tickets for stopped Codex threads or, with feature `history.claude`, Claude Code conversations in granted projects; raw native IDs stay on desktop, and an imported Claude conversation runs in restricted mode. Memory belongs to the conversation's project on its memory server, whichever provider it uses; the phone reaches it only while that server is granted. It offers paged browse/recall, saved-note CAS, exact-preview-bound forgetting/clearing with rechecked erasure receipts, and typed, revision-bound history (`memory.timeline`), corrections, conflict resolution, identity decisions and episode freezing, each witnessed by the person's own statement; `memory.health` reports degradation without endpoints, models or error text. Remote graph inspection/erasure has a conservative worker-side work quota; large graphs require desktop maintenance.

New APIs must be added to the strict schemas, capability map, implementation, golden/schema checks and scope/uncertainty regressions together. Planned methods without implementations must remain absent from negotiation.

## Versions, features and build identity (1.1)

Welcome carries `protocol: {major: 1, minor: 1}`, a `features` list and `build: {version, commit, dirty}` from the installed build's `build-info.json` (`brokerBuild` is derived from it). The hello's `protocolMin`/`protocolMax` revision range stays 0–0; a client outside it is closed with 4010 `INCOMPATIBLE_CLIENT_NEWER` or `INCOMPATIBLE_CLIENT_OLDER`, which Android explains by naming the side to update while keeping its drafts. Minor versions only add: an operation is used only when it is in the negotiated `operations`, and a new request parameter or behaviour only when its feature is named. Features in 1.1 (described in `CONTRACT.json`): `activity.page` (Activity with a continuation cursor), `sessions.batch` and `search.ids` (no silently hidden sessions or matches), `message.sources`, `citations.display` (`settings.showMemoryCitations`), `agent.refs` (agents and approvals name agents by opaque HMAC references, never native thread IDs), `captures`, `drafts.desktopAttachments`, `messages.bookmarks`, `workflows.status`, `sessions.behavior`, `desktop.portrait`, `desktop.workspace`, `memory.health`, `sessions.focusTerminal` and `history.claude`.

Desktop delivery to the native UI is bounded per client and globally; a client that falls behind receives one `resync` event (or is closed) instead of unbounded queued frames. A phone whose socket buffers more than 8 MiB is closed as a slow consumer and reconciles on reconnect; Android bounds its own inbound frame processing and coalesces session upserts per connection.

## Captures, desktop draft attachments and companion views (1.1)

`captures.start` begins an accepted job (`capturing`, `editing` while Satty is open on the desktop, then `ready`, `attached`, `cancelled`, `failed` or `expired`) announced by `capture.updated` events. A ready image is immutable and named by its digest; the phone previews a reduced copy (`captures.preview`, read with `attachments.read`) and `captures.attach` turns exactly that original into a ready upload of one conversation. Nothing reaches a provider until that message is sent. Revocation, a scope change, Stop and shutdown cancel open captures.

The open conversation's session DTO lists its desktop draft attachments (`draftAttachments`: id, name, kind, MIME type, size, SHA-256; never a path). `drafts.attachmentPreview` shows a text file's opening or a reduced image bound to the original's digest. `drafts.put` with `desktopAttachmentIds` keeps exactly those attachments (removing one is explicit); without it a draft that has attachments cannot change. `sessions.send` with `desktopAttachments: [{id, sha256}]` sends them exactly as reviewed and is refused when they changed, were not reviewed, or the send would be queued.

Pinned replies are the desktop's bookmarks (`bookmarked` on messages, `messages.bookmark`, `messages.bookmarks`). `sessions.behavior` says which style a conversation uses and whether it is set for the conversation, the project or everywhere. `workflows.status` lists a conversation's results, keeping the provider's report apart from Cere's own verification, and the schedules made from it; `workflows.pauseSchedule` can only pause one. `desktop.portrait` serves the still status portrait, `desktop.workspace` the project's workspace card from fresh observations only, and `sessions.focusTerminal` brings a linked conversation's terminal forward through the windows category.

## Trusted-device mode and replacement pairing (0.1.2)

The signed offer may include `actionAuthentication: "biometric" | "trusted-device"` (absent means biometric) and `replacesDeviceId` (a live same-desktop phone UUID). Every included field participates in the original JSON signature and offer digest; clients must not insert omitted defaults or remove unknown fields when calculating them. The response format is unchanged. The broker stores the policy from its own pending offer and includes it in welcome and `devices.self`. Android signs proof-required actions silently only when trusted policy matches both the saved pairing and authenticated welcome. No additional mutation accepts connection-key proofs.

Replacement is explicitly initiated on the desktop. The phone verifies saved desktop/device identity and key continuity, refuses unresolved operations, and persists the new pairing together with retained drafts/cache before deleting old aliases. The broker reuses matching project IDs, revokes the replaced device, stops its native work, and transfers retained authorized session ownership. Local certificate/address renewal preserves the identity and TLS key but changes the pinned certificate, so each phone needs replacement pairing.

Ollama session DTOs advertise `canQueue` and `queuedCount`. A signed `sessions.send` during a busy Ollama turn can return `status: "queued"` with its reserved `turnId`. Acceptance durably records the message and consumes the CAS-protected draft. Follow-ups dispatch FIFO after the current turn settles; Stop, shutdown, restart, or a failed turn leaves unsent messages visible without replaying them. Dispatch revalidates configuration and device authority. Approval DTOs include `parentSessionIds` so parent conversations can display delegated requests even when session summaries are paged. Conversation history includes question/answer and queued/cancelled message rows.
