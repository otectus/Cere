# Sideload releases

Development download: [Cere Mobile 0.1.3 debug APK](https://github.com/otectus/Cere/releases/download/mobile-dev-v0.1.3/cere-mobile-v0.1.3-debug.apk), published under the prerelease tag [`mobile-dev-v0.1.3`](https://github.com/otectus/Cere/releases/tag/mobile-dev-v0.1.3). Its `dev.otectus.cere.mobile.debug` package and signing certificate match the previously installed development build, allowing an in-place upgrade. This manual download is separate from the stable update checker and signing workflow below. Stable releases still require the owner's permanent signing key and completed hardware gates.

The latest published download is the 0.1.3 development build above. The source is version **0.1.4 (1004)**, which has not been published; candidate APKs built from it for review are not releases. Update this paragraph and the download link only after a build is actually published.

Tags are `mobile-vX.Y.Z`; the Android `versionName` must be `X.Y.Z`, and `versionCode = major*1000000 + minor*1000 + patch`, with each component below 1000. Do not reuse/downgrade a released version. Stable package: `dev.otectus.cere.mobile`; debug: `.debug` suffix.

Development snapshots are built with `./gradlew :app:assembleDev` (`app/build/outputs/apk/dev/app-dev.apk`): the release build's R8 optimization, not debuggable, under the development package `dev.otectus.cere.mobile.debug` and the debug signing key, so earlier development installs upgrade in place. That key lives in the builder's Android user directory (`debug.keystore`); back it up, because a snapshot signed by another key cannot update an existing install, which then needs uninstalling and pairing again. Publish snapshots as prereleases tagged `mobile-dev-vX.Y.Z` with `cere-mobile-vX.Y.Z-dev.apk` and a `mobile-development.json` that names the package, `development: true`, version name and code, `minSdk`, protocol range and the APK name and SHA-256. `ANDROID_HOME=… SOURCE_COMMIT=… node tools/mobile-release.ts mobile-dev-vX.Y.Z app-dev.apk CERT_SHA256 OUTPUT` checks the APK's package, version, minSdk, signer and that it is not debuggable, then writes those files (`SOURCE_DIRTY=1` marks a build with uncommitted changes, which must not be published). A development install's update check follows only those prereleases; stable installs never see them.

Before publishing a snapshot, `node tools/mobile-upgrade-check.ts --old-apk … --old-test-apk … --candidate-apk …` installs the previous snapshot on a test emulator, pairs it with its own source's `UsbPairingSetupTest`, seeds an open conversation and an unsent draft through its UI, installs the candidate over it, and checks that the same device signs in with the draft and selection kept and that one signed send is recorded once. `node tools/mobile-ui-pairing-check.ts --apk …` pairs an R8 build through its own pairing screen by network return.

### Updating a 0.1.3 development install

The 0.1.3 snapshot's update check looks only for stable releases, so it never offers a later development snapshot: update it once by hand. On the phone, open the snapshot's GitHub release page, download `cere-mobile-vX.Y.Z-dev.apk`, check its SHA-256 against `SHA256SUMS`, then open it and choose **Update** in Android's installer. Do not uninstall Cere Mobile first and do not clear its data: the update keeps the pairing, its keys, the encrypted conversations, drafts and the open conversation because the package (`dev.otectus.cere.mobile.debug`) and the signing certificate (SHA-256 `3aac29551b21d4d295e500a7c9c6ef3697e9877c270e5056282f844cad73562b`) are unchanged. Android refuses an APK signed by any other key as an update; uninstalling to get around that erases the pairing and needs pairing again. Update and restart the desktop broker as well before relying on the new behaviour. From that build on, **Check for updates** in Settings finds later development snapshots.

`.github/workflows/mobile-check.yml` runs secretless contract, broker, Kotlin, lint and APK builds (debug, test, release and development) with commit-pinned Actions, then the instrumentation suite and an R8 development-build launch on an API 35 emulator. `.github/workflows/mobile-release.yml` builds the same gates for mobile tags, then uses a protected `mobile-release` environment to sign the tested unsigned artifact, verify signer/package/version, generate checksums/metadata, attest the APK and upload a **draft** GitHub release. It does not publish the draft automatically.

Before enabling signing, the repository owner must configure required reviewers and mobile-tag restrictions for that environment. A YAML environment name does not configure GitHub's protection rules. Create the permanent keystore offline, retain an encrypted offline backup, and record recovery ownership. Required environment secrets:

- `MOBILE_KEYSTORE_BASE64`, `MOBILE_KEYSTORE_PASSWORD`, `MOBILE_KEY_PASSWORD`, `MOBILE_KEY_ALIAS`.
- Environment variable `MOBILE_SIGNING_CERT_SHA256`: expected 64-character certificate digest.
- A committed evidence record, `docs/mobile/release-evidence/mobile-vX.Y.Z.json` (see that directory's README), certifying the exact unsigned APK bytes, signer, tested source commit, desktop build, device/OS, date and every required hardware gate. `tools/mobile-release-evidence.ts check` refuses to sign when any of them differs; a record cannot certify a different APK or later source changes. This replaces the former `MOBILE_HARDWARE_GATES=passed` variable, which could certify new code automatically.

The release job fails without these values. It also checks 16 KiB page alignment of the signed APK (`zipalign -c -P 16`, saved as `ZIPALIGN-16K.txt`). Secrets are passed to apksigner through environment references, the temporary keystore is removed, and no secret-bearing job is exposed to pull requests. Approve only reviewed source/tags. Never check in a keystore, its passwords or a signing identity generated casually by CI.

Assets are `cere-mobile-vX.Y.Z.apk`, `SHA256SUMS`, `SIGNING-CERTIFICATE-SHA256.txt`, `mobile-release.json`, `RELEASE-EVIDENCE.json`, APK verification and 16 KiB alignment output, CycloneDX dependency inventory, notices and build provenance. `mobile-release.json` names the protocol the APK speaks (`protocol.major`, hello revisions `minMinor`–`maxMinor`, the newest desktop minor it understands and the features it uses when offered), the source commit, and the evidence record's SHA-256. `tools/mobile-release.ts` verifies the actual APK package, version, minSdk and signer before producing metadata. Runtime dependency hashes come from `tools/mobile-sbom.gradle`; an inventory is not a substitute for dependency-license review.

The app's manual and at-most-daily foreground Settings check queries up to ten GitHub Releases pages with ETags, bounded bodies/timeouts and no token. A stable install accepts only published stable mobile tags with matching APK and metadata, higher versionCode, supported Android level and protocol 1 at hello revision 0; a development install applies the same checks to development snapshots whose metadata names its own package. It opens the exact GitHub release page for user-controlled installation. Rate limits/offline checks never affect chat. There is no silent install or `REQUEST_INSTALL_PACKAGES` flow.

For Obtainium, use `https://github.com/otectus/Cere`, filter release tags with `^mobile-v[0-9]+\.[0-9]+\.[0-9]+$`, and APK assets with `^cere-mobile-v[0-9]+\.[0-9]+\.[0-9]+\.apk$`. Exclude prereleases. Verify the first install's signing fingerprint against the owner's separately retained value. Android requires the same signer for future in-place updates. Test those filters against an actual draft/staged release before recommending unattended updates.

Maintain release notes with protocol/minimum-desktop compatibility and measured device/VPN/battery behavior. Notable changes are recorded under **Unreleased** in the repository's [CHANGELOG.md](../../CHANGELOG.md); before tagging, bring the phone-facing part into [RELEASE-NOTES.md](RELEASE-NOTES.md), which the release job uses as the draft's notes. Complete [TESTING.md](TESTING.md) gates before making the GitHub draft public.
