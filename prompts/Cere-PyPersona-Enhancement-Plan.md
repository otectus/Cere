### Cere: a native companion with a durable broker

**Purpose and stack.** Cere is an Arch Linux/Hyprland desktop companion: animated avatar, compact chat, expanded workspace, desktop controls, persistent AI sessions and an optional Android client. `C:CMakeLists.txt` specifies C++20, Qt 6.8+ and LayerShellQt. The broker is ESM TypeScript executed by Node; `C:package.json` declares Node >=24, while `.node-version`/README document the validated 26.8.2 runtime. SQLite/FTS5, Neo4j projections, a Qdrant adapter, and separate Python speech workers support selected features. This is not an Electron or Python desktop application.

**Architecture.** `C:native/main.cpp` starts the UI; `native/controller.cpp` owns QML views, connection/reconnection, drafts and attention. `C:broker/main.ts` starts a private, same-user Unix-socket JSON-lines service. `broker/core.ts::Core` composes storage, providers, permissions, memory, tools, speech, telemetry, recovery and workflows. `qml/Panel.qml` and `qml/Workspace.qml` reuse `qml/Shell.qml`; the pet and approval bubble are additional surfaces over the same broker state. The optional `broker/remote/` gateway is separate from local IPC.

`C:broker/types.ts::Adapter` is the provider boundary. Codex app-server and Claude headless adapters live in `broker/providers.ts`; AntiGravity in `broker/antigravity.ts`; Ollama in `broker/ollama.ts`; direct OpenAI, Anthropic and Google APIs in `broker/api-providers.ts`. `broker/mcp.ts` exposes Cere's own capabilities to managed CLI sessions. It is not a general incoming third-party MCP-client manager.

**Data and settings.** `C:broker/types.ts` defines sessions, messages, drafts/view anchors, attachments, approvals, child-agent status, projects, completions and settings. `broker/store.ts` stores normal state in an owner-only SQLite WAL database and temporary sessions in a separate in-memory database. Structured API/Ollama history is retained separately from displayed messages; CLI providers own native histories. `broker/credentials.ts` keeps API credentials outside general settings. Settings use validated defaults, revision checks and targeted updates.

**Interaction loop.** A QML action passes through the native controller to `Core.rpc`. `Core.sendTurn` validates current authority, session/draft revision, attachments and provider capabilities, persists submission state, then dispatches a generation-bound adapter. Provider events update the transcript and Activity; tool calls pass through typed definitions and authorization; questions and permissions use dedicated forms. Completion queues speech and inbox/pet feedback. Stop cancels provider/tool/child work. Restart recovery marks interrupted work and avoids automatically replaying ambiguous actions (`broker/send-queue.ts`, `broker/recovery.ts`, `broker/core.ts`).

API/Ollama turns share the bounded loop in `C:broker/ollama.ts`: personality, time/project context, selected memory/telemetry, web results, history, streaming and tool rounds. `workingContext` trims complete old turn groups and oversized tool material against approximate capacity; it does not provide a rolling narrative summary. CLI-native compaction is a different mechanism.

**Memory.** `C:broker/memory.ts` integrates a dedicated graph-memory worker. `broker/graph-memory/canonical.ts` and `broker/graph-memory/schema.ts` make SQLite authoritative for evidence, assertions, temporal validity, scope, lineage, retrieval artifacts and erasure. Neo4j/Qdrant are rebuildable projections. Retrieval combines lexical/vector/entity/graph evidence, validates candidates against current policy and provenance, and emits bounded untrusted-context packets. `broker/memory-review.ts`, `qml/MemoryReview.qml` and `qml/GraphMemoryInspector.qml` already support review, correction and “why recalled?” workflows.

This memory implementation is explicitly experimental. `C:docs/memory/implementation-report.md` and `evaluation.md` report incomplete effective identity merge/split and active-task relationships, an unevaluated current default extractor, and an unmet graph-ranker improvement gate. Rich schema is not evidence of validated semantic quality.

**Personality, expression and voice.** `C:broker/personality.ts` provides one global editable personality and literal assistant name, with explicit permission/task precedence. Avatar, name, personality and voice are independent. `qml/PortraitMood.js`, `qml/MoodSource.qml` and `qml/ConversationMood.qml` infer transient visual tone; they do not implement durable emotions or model-facing needs. Speech already supports local engines, IndexTTS and ElevenLabs (`broker/tts.ts` and engine modules). Local whisper.cpp-style input has cancellation and an editable transcript review (`broker/transcription.ts`, `qml/VoiceInput.qml`).

### PyPersona: a persona-enabled AI workbench

**Purpose and stack.** PyPersona 1.2.0 is a cross-platform PyGPT fork. Python 3.10–3.13, PySide6/Qt Widgets, QtWebEngine/legacy transcript rendering, SQLAlchemy/SQLite, model SDKs, LlamaIndex and plugin/provider registries support chat, agents, research, documents, images, audio and a browser companion. `P:pyproject.toml` still makes 100+ runtime dependencies mandatory; its named extras are additive labels, not a minimal default install.

**Architecture and loop.** `P:run.py`/the console entry call `p/app.py::run`, register providers/plugins/tools, then launch `p/launcher.py`. `p/app_core.py::Core` exposes services through `window.core`; controllers and widgets share the window graph. The central path is `p/controller/chat/input.py` → `controller/kernel/kernel.py` → `controller/chat/text.py` → `core/bridge/bridge.py` → `core/bridge/worker.py`. Input is stored before execution; final persona/memory prompt preparation runs in a worker, with send-time model/mode snapshots. Provider streams return through response/output controllers and kernel events. Output handlers update memory, run optional style/contract checks and continue tool/agent work. `core/dispatcher/dispatcher.py` routes events and isolates individual plugin exceptions.

**Data models.** `P:p/item/ctx.py` separates `CtxMeta` conversation metadata from `CtxItem` turns, attachments, tool calls/results and token counters; runtime trust snapshots are not serialized as reusable permission. `core/bridge/context.py::BridgeContext` carries the request. `item/preset.py` is the existing preset substrate: promoted `item/persona.py::PersonaItem` values live in `PresetItem.extra['persona']`. Persona selection resolves the active preset for a mode, avoiding a second conflicting selector. Style profiles and projects are distinct models.

**Memory is several systems, not one.** Thread summaries live in context extras; persona-global episodic/semantic records live in JSONL files; temporal graph memory has a SQLite backend plus journal and optional remote backends; document-oriented Chat Memory has a collection/source registry in a separate SQLite database with existing index namespaces. The actual graph prompt retriever differs from a legacy query API that remains empty. Some observation/relationship structures are dormant. These distinctions matter when adapting ideas to Cere's already unified canonical memory.

**Configuration and UX.** Versioned defaults, JSON settings, presets/styles, SQLite data and indexes live under a selected work directory. Full workdir profiles are separate from Personas. Credentials remain plaintext in configuration, as README discloses. The UI includes mode/model/preset selectors, plugin controls, configurable send keys, notes, projects, inspectors, audio controls, tools and a local browser portal. Its graph/document/search inspectors and typed settings are useful patterns; reproducing all its panels would conflict with Cere's compact design.

### Phase-1 conclusion

Cere already owns the desktop authority boundary, persistent broker, expressive avatar, voice pipeline and substantial memory infrastructure. PyPersona's strongest additional ideas are structured reusable behavior, explicit prompt/context composition, knowledge collections, inspectable recall, and bounded workflow controls. The following phases evaluate those mechanisms individually rather than assuming that a larger feature list warrants a larger Cere application.

### Maturity distinctions that affect reuse

1. **Do not inventory comments as completed features.** `TemporalGraphMemoryProvider.query()` returns empty; active prompt graph recall is `retrieve_context_chunks`. `RelationalRecord` and graph observations are modeled but dormant. Graphiti adapters are stubs. Chat Memory reranker/query rewrite and its citation helper's inspector integration are explicitly deferred. Style custom `render_template` is inert.
2. **Graph setting completeness is partial.** Persona/global graph settings expose extraction temperature/template/chunk size/overlap. The inspected GraphIngestor creates the built-in MemoryExtractor and uses provider/model/max-tokens/max-facts; it does not consume those template/temperature/chunk controls. Its Ollama completion receives the model but does not apply the max_tokens local variable. Configuration exposure is not proof of effective behavior.
3. **Semantic pin math is weaker than its docstring.** `P:src/pypersona/core/persona/scoring.py` multiplies exponential decay by ten for pinned records, so pinned values still eventually decay below threshold. The docstring's indefinite survival assertion is mathematically false.
4. **Graph recall score configuration is wider than actual scoring.** `_score_fact` sums semantic/confidence/importance/pin/recency. Other declared weights are not applied there.
5. **Conviction labels describe implementation heuristics.** A human pin yields EMPIRICAL and a supersession yields DERIVED; neither proves truth. Repeated model assertions/consensus are not independent evidence.
6. **Conceptual conflict behavior is single-valued.** It closes different objects for the same subject/predicate. Multi-valued facts require different semantics; code ingestion explicitly handles them differently.
7. **Capture/recall are separate.** Code parser/ingestor/decision APIs exist; prompt code recall and analyzer are wired. No verified production capture caller was established in this review; do not treat it as always-on code understanding.
8. **Deletion variants have different meanings.** Graph archive preserves event history; compaction intentionally removes active history but creates a backup; collection deletion attempts vector purge but catches errors. These are not interchangeable privacy/forget operations.
9. **Chat Memory source type and settings need caution.** Model types include web/note but ingestion calls existing `index_files` with paths; actual format support follows that downstream stack. Stored collection embedding_model/chunk_size/chunk_overlap are not applied by this ingestion wrapper; only provider override is used. Scope pinning is global on the collection object, and session scope is not tied to a run ID in ScopeResolver.
10. **Chat Memory automatic plugin injection scope is incomplete.** `plugin/idx_llama_index/plugin.py::_inject_chat_memory` passes chat_id/persona_id but not project_id; it takes persona_id from config preset rather than the per-mode persona resolver. Do not claim project-aware automatic recall on that path.
11. **Model exceptions often degrade silently/diagnostically.** Most memory operations return empty/no-op and log rather than blocking chat. That preserves interaction availability but makes explicit health/status surfaces important for diagnosing missing memory.

The harness has additional execution limits: its default helper runner performs no model work; skill invocation returns `invoked:false`; cache planning is advisory; structured-output validation lacks a verified runtime caller; loaded snapshots are data rather than resumed kernels; token/cost counters are not wired. The separate MCP plugin is real and must not be confused with the harness MCP seam. The workbench’s lifecycle helper classes likewise do not establish application-wide scheduling, and their shutdown budgets are soft accounting.

## 4. Proposals

### Decision rules and summary table

The plan contains **39 composable proposals**, not 165 separate projects. Multiple inventory rows often describe different layers of the same feature. All changes stay in Cere’s native QML/C++ and TypeScript broker architecture; memory remains canonical in SQLite, and managed CLI providers retain their own execution contracts. No proposal is an unrestricted direct code port: the useful transfers are adaptations or architectural inspiration. Direct reuse of small algorithms/test fixtures can be assessed during implementation with the license notices below.

**Effort** is a relative engineering estimate: small = a bounded vertical slice using current interfaces; medium = several coordinated modules or a new workflow; large = a new execution/ingestion/transport boundary or substantial semantic validation. It is not a calendar commitment. **Rank** is a qualitative benefit-to-effort judgment assuming Cere’s primary role remains a native desktop/development assistant. Dependencies can require a lower-ranked foundation before a higher-ranked feature. P0 = near-term low-risk value; P1 = next useful increment; P2 = demand-driven expansion; P3 = optional product direction. Acceptance criteria below are proposed implementation gates, not tests run during this review.

Every proposed **new** file is a target design, not evidence that it already exists. When a later proposal refers to a module introduced by an earlier one, it extends that same module. UI compatibility is assessed against the verified historical overhaul direction/current main, pending access to any unpublished branch tip.

Prefer a narrow existing protocol/adapter; review the exact dependency and transitive licenses if adding a worker. PyPersona’s 100+ hard requirements are not an optional-dependency design to copy. |
| Bundled artwork, fonts, prompts, example content or media | Do not infer they all carry the root code license. Check file-level provenance and license before copying; existing Cere avatar/voice choices remain independent. |
| Speech/models/media tools | Cere’s `packaging/tts-NOTICES.md` and `PKGBUILD` document component-specific terms including eSpeak `GPL-3.0-or-later` and the Amy voice’s CC-BY-SA notice; IndexTTS/model use has separate conditions. New voices, weights, FFmpeg builds and cloud media providers need their own concrete version/redistribution/service review. Installing a model is not the same as owning its redistribution rights. |
| Neo4j, Qdrant, optional vector stores and provisioners | Keep current supported versions/manifests and source-of-truth design. Do not add LanceDB/Zep/Graphiti or Docker merely for source parity; licenses, editions, credentials and operational ownership would require a specific need. |
| External APIs and OAuth services | Source presence proves a client exists, not that present-day endpoints, scopes or terms still work. Verify official APIs, authentication scope and price limits for the selected integration at implementation time. |

### Top three quick-win implementation sketches

These are proposed diffs, not patches already applied. Each reuses the current UI and broker contract rather than adding a parallel subsystem.

#### Q01 — Behavior preset catalog

Add a bounded version-1 catalog through existing `Store.get/set`, with stable IDs, labels, validated text, per-item/catalog revision and update time. New RPCs list/save/delete entries; they do not call `updateSettings`. Add the catalog key to `broker/recovery.ts::machineMeta` so restoring conversation state preserves current local preferences.

```text
catalog = { schema: 1, revision, items: [{ id, label, text, revision, updated }] }

savePreset(input, expectedRevision):
    validate exact fields, bounded label/count, validatePersonality(input.text)
    reject a stale catalog/item revision
    persist updated catalog; publish catalog-changed state
    // No settings change, provider restart, model call or permission change.

loadPresetIntoEditor(preset):
    require an intentional replacement if the editor contains an unsaved draft
    editor.text = preset.text
    // Do not adopt a new saved baseline, edit the name, or change active settings.

applyEditor():
    use the existing settings.update call with personality, assistantName,
    expectedRevision: savedRevision and expectedIdentity (personality/name/avatar baselines)
```

`qml/PersonalitySettings.qml` gets a compact chooser using existing `CComboBox`/`CButton`/`CField`. “Load into editor” and “Save changes” remain distinct. Deleting or changing a catalog entry never changes already-applied text. Focused acceptance checks: restart persistence; stale-save rejection; load→dirty→discard/save; unrelated settings updates retain the draft; name/avatar/voice/model/authority remain independent; restore retains the catalog. No new database table or external dependency is needed.

#### Q02 — Recipe starters and a palette destination

Extend `broker/workflows.ts::builtinBasis` with stable version-1 definitions, typed inputs, explicit expected output, honest permission description, `maxTurns: 1` and bounded runtime. Reuse `prepareRecipe → exact preview → createRecipeDraft → user Send`; do not duplicate existing review-diff/diagnose-crash/prepare-release/explain-error definitions.

```text
CommandPalette.buildEntries():
    add { id: 'page:recipes', kind: 'workflow', title: 'Project recipes', ... }

CommandPalette.activate(workflow entry):
    record navigation('page:recipes')
    emit workflowsRequested(); close palette

Shell: workflowsRequested -> Workflows.openRecipes()
Workflows.openRecipes(): requestedTab = recipesTab; open()
Workflows.onOpened():
    tab = requestedTab; requestedTab = projectTab
    refresh only the selected tab

selected recipe + typed inputs -> existing exact preview
reviewed preview -> existing draft creation -> separate user Send
```

The `page:` ID already fits navigation recents/favorites validation. A one-shot requested tab matters because current `Workflows.onOpened` resets to the project tab; simply setting `tab` before opening would fail. Respect the dialog’s existing single request-ID gate rather than concurrently loading both tabs. Check palette Enter in compact/workspace, focus restoration and that open/preview cannot send, execute, approve or overwrite the active draft. Existing source-change/digest/expiry guards remain the authority.

#### Q03 — Pure shared-renderer personality preview

Add `personality.preview` to Core’s read-only RPC set. Validate editor personality/name with the existing validators; snapshot saved identity and settings revision synchronously. Do not initialize a provider, recall memory or enter the mutation/recovery gate.

```text
personality.preview(input):
    validate allowed fields
    draft = { text: validatePersonality(input.personality),
              name: validateAssistantName(input.assistantName) }
    saved = current settings identity + current settingsRevision
    return {
      scope: 'cere-personality-block',
      draft: personalityInstructions(draft.text, draft.name),
      saved: personalityInstructions(saved.text, saved.name),
      settingsRevision: saved.revision,
      matchesSaved: draft.text == saved.text && draft.name == saved.name
    }
```

Show an optional preview disclosure with draft/saved labels and the caption “Cere’s personality block. Provider and project instructions may add other context.” Use a separate preview request ID/editor fingerprint from Save; drop stale responses after edits or label a stale saved comparison. Check exact renderer equality for default/custom/empty/Unicode cases, identical validation failures, zero writes/network/recall, and stale-response handling. Character count is honest for this slice; full-context token precision is not.
